# **What Is Trigonometry?**  
Trigonometry is a branch of mathematics that studies the **relationships between angles and lengths** in triangles.  
The word comes from Greek:

- **trigonon** = triangle  
- **metron** = measure  

So **trigonometry = the study of measuring triangles**.

At its heart, trigonometry answers questions like:

- “If I know one side, can I find the others?”  
- “If I know an angle, what is the height of a building?”  
- “How do waves, circles, and rotations behave?”

---

# **Why Is Trigonometry Important?**

Trigonometry appears everywhere:

- **Engineering**: designing bridges, motors, robots  
- **Physics**: waves, forces, rotations, vectors  
- **Architecture**: building angles, slopes, heights  
- **Astronomy**: distance to stars, planetary motion  
- **Navigation & GPS**: directions, bearings  
- **Computer graphics**: animations, 3D models, games  

In GASING-style teaching, trigonometry becomes simple because it starts with **intuition**, then **pattern**, then **formula**—always dari mudah → menengah → sulit.

---

# **The Core Idea: The Right Triangle**

Almost all basic trigonometry starts from **one picture**:

A **right triangle** with one 90° angle.

Given an angle θ, we label the sides:

- **Opposite** = the side opposite the angle  
- **Adjacent** = the side next to the angle  
- **Hypotenuse** = the longest side  

From here, trigonometric ratios are born.

---

# **The Three Main Trig Functions**

These tell us how the sides relate to the angle.

1. **Sine (sin θ)**  
   \[
   \sin θ = \frac{\text{opposite}}{\text{hypotenuse}}
   \]

2. **Cosine (cos θ)**  
   \[
   \cos θ = \frac{\text{adjacent}}{\text{hypotenuse}}
   \]

3. **Tangent (tan θ)**  
   \[
   \tan θ = \frac{\text{opposite}}{\text{adjacent}}
   \]

In GASING, this is often taught with **rotating vectors**, so children see sin/cos not as formulas, but as **coordinates of a turning point** on a circle.

---

# **The Unit Circle (Lingkaran Satuan)**

As mathematics grows, trigonometry moves from triangles into circles.

If you take a circle with radius 1 (unit circle), then for a point moving around the circle:

- x-coordinate = **cos θ**
- y-coordinate = **sin θ**

This makes trigonometry extremely powerful because **angles become positions**.

---

# **Special Angles**

Certain angles have exact values:

| Angle | sin | cos | tan |
|------|-----|------|------|
| 0°   | 0   | 1    | 0    |
| 30° | 1/2 | √3/2 | 1/√3 |
| 45° | √2/2 | √2/2 | 1 |
| 60° | √3/2 | 1/2 | √3 |
| 90° | 1 | 0 | undefined |

These come naturally from **GASING triangles** (30–60–90 and 45–45–90).

---

# **Useful Identities (Hubungan Penting)**

These help simplify complex expressions:

### 1. **Pythagorean identity**
\[
\sin^2 θ + \cos^2 θ = 1
\]

### 2. **Tangent identity**
\[
\tan θ = \frac{\sin θ}{\cos θ}
\]

### 3. **Angle sum formulas**
\[
\sin(a + b) = \sin a \cos b + \cos a \sin b
\]

and so on.

These are foundations for deeper math (calculus, physics, waves).

---

# **Applications**

### **1. Heights & Distances (Surveying)**
Use tan θ to find the height of a tower from far away.

### **2. Navigation & Bearings**
Direction of an aircraft or ship uses sin & cos.

### **3. Waves**
Every wave—sound, light, electricity—is a sin/cos curve.

### **4. Rotations & Vectors**
Robots, drones, and animations use trig for turning and coordinates.

## 2. Adder Blocks – Blueprint

### 2.1 Functional Role

Adder blocks replace:

- MAC units  
- FP ALUs  

with:

- **integer adders**  
- **accumulators**  
- **bitwise popcount (for binary nets)**  

They are the fundamental compute primitives for:

- matrix-vector operations (W·x approximated as additive)  
- attention (Q·Kᵀ approximated with additive scoring)  
- MLP layers (sum of LUT’d activations + biases)

---

### 2.2 Adder Block Structure

Each **Adder Block** is a SIMD-style engine:

```text
+------------------------------------------------+
|               ADDER BLOCK (AB)                 |
+------------------------------------------------+
|  Vector Input Register File (VIRF)             |
|  Vector Weight Code Register File (VWCRF)      |
|                                                |
|  +------------+   +------------+   +--------+  |
|  | ADDER LANES|...| ADDER LANES|   | POPCNT |  |
|  | (N-LANES)  |   | (N-LANES)  |   | UNIT   |  |
|  +------------+   +------------+   +--------+  |
|                                                |
|  Accumulator Array (ACC)                       |
|  Saturation & Clip Unit (SCU)                  |
+------------------------------------------------+
```

**Key Components:**

1. **Vector Input Register File (VIRF)**  
   - Stores activations / input slices  
   - Width: e.g. 256–1024 bits per register  
   - Depth: enough to hold tile’s working set (e.g. 32–64 regs)

2. **Vector Weight Code Register File (VWCRF)**  
   - Stores compressed weight *codes* (not raw weight values)  
   - Weight codes are indices into LUT (2–4 bits each)  

3. **Adder Lanes (AL)**  
   - Each lane: k-bit signed adder (e.g. 8 or 12 bits)  
   - N lanes per block (e.g. 32 / 64 / 128 lanes)  
   - Operate in parallel on vector chunks  
   - Optional pipeline stages for higher clock

4. **Popcount Unit (for binary models)**  
   - Implements XNOR + POPCOUNT path for binary weights/acts  
   - Output integrated as “pseudo dot product” via addition  
   - Useful in extreme energy-saving mode

5. **Accumulator Array (ACC)**  
   - Stores partial sums for an output vector / neuron batch  
   - Each accumulator ~16–24 bits to handle accumulation depth  

6. **Saturation & Clip Unit (SCU)**  
   - After accumulation, values are clipped to target bit-width  
   - Implements e.g. linear quantization or simple clipping  

---

### 2.3 Data Path (Per Cycle, Simplified)

1. Load:
   - VIRF ← activations from Local Scratchpad  
   - VWCRF ← weight codes from LUT / SRAM  

2. For each lane:
   - Resolve weight value via LUT or sign/bit pattern  
   - Perform addition or bitwise operation  
   - Update ACC (accumulator)  

3. After all input chunks processed:
   - ACC → SCU → quantized output  
   - Write back to Local Scratchpad or Global SRAM  

The **core idea**:  
> Instead of `sum(w_i * x_i)`, we do `sum( LUT(w_code_i) + f(x_i) )` or bitwise approx.

## 3. LUT Blocks – Blueprint

### 3.1 Roles of LUTs

GASING-AI uses LUTs heavily for:

- Weight value decoding (from codes)  
- Activation functions (ReLU, GELU≈, etc.)  
- Positional encodings  
- Attention score approximations  
- Quantization / dequantization maps  

---

### 3.2 LUT Block Bank (LBB) Structure

```text
+------------------------------------------------------+
|                  LUT BLOCK BANK (LBB)               |
+------------------------------------------------------+
|  Weight LUTs (WLUT)                                  |
|   - Per-layer / per-tile small SRAMs                 |
|   - Each entry: small signed integer                 |
|                                                      |
|  Activation LUTs (ALUT)                              |
|   - Input: quantized integer                         |
|   - Output: transformed integer                      |
|                                                      |
|  Positional Encoding LUTs (PELUT)                    |
|   - index → small vector components                  |
|                                                      |
|  Attention Score LUTs (ASLUT)                        |
|   - similarity index / code → score approximation    |
+------------------------------------------------------+
```

### 3.3 Implementation Details

- Physically: small **single-port or dual-port SRAM blocks**  
- Access time: 1–2 cycles  
- Address:
  - For weights: **2–4 bit code** → LUT index  
  - For activations: **8–10 bit** → ALUT index  
  - For positions: sequence index modulo [PE size]  
- Data width:
  - WLUT: 8–12 bits signed  
  - ALUT: 8–12 bits signed  
  - PELUT: vector of small ints (e.g. 4×8 bits)  

Each **Adder Tile** can have:

- 1 WLUT group per layer group  
- 1 shared ALUT  
- 1 shared PELUT for positional encodings

## 4. Memory Hierarchy & Access Patterns

### 4.1 Memory Hierarchy

1. **Global On-Chip SRAM (G-SRAM)**  
   - Stores model weights (compressed) + frequently used activations  
   - Size: e.g. 64–512 MB depending on process / product tier  
   - Access via interconnect to all tiles  

2. **Local Scratchpad (LSP) per Tile**  
   - Size: e.g. 256–1024 KB  
   - Stores:
     - current layer’s input activations  
     - partial outputs  
     - small local K/V caches for attention  

3. **LUT SRAM** (inside LBB)  
   - Small: typically a few KB per LUT  
   - Very low latency  

4. **Instruction / µCode Memory**  
   - Stores micro-instructions for tile sequencing  
   - Could be on same die or separate ROM/flash  

5. **Off-chip DRAM / Flash (optional)**  
   - For large models or multi-model storage  
   - Weights loaded into G-SRAM in chunks (tiling)

---

### 4.2 Dataflow Pattern for “Matrix-Vector” Style Ops

We use a **weight-stationary or output-stationary** style depending on block type.

#### Example: Dense Layer (output = W · x)

**Assumptions:**

- W: [M × N] matrix (quantized)  
- x: [N] activation vector  
- y: [M] output vector  

**Flow:**

1. **Preload:**
   - Tile reads slice of x into LSP  
   - Tile reads a block of weight codes from G-SRAM into VWCRF / local weight buffer  

2. **Loop (over N in chunks):**
   - Load chunk of x from LSP → VIRF  
   - Broadcast same x chunk to all lanes  
   - For each lane:
     - Read corresponding weight codes → LUT → weight ints  
     - Compute addition/bitwise update to ACC  

3. **Post:**
   - Once all chunks processed, ACC → SCU (clip/quant) → y_slice in LSP/G-SRAM  

This is **output-stationary**: each output element’s accumulator stays local until done.

---

### 4.3 Dataflow Pattern for Attention (Q·Kᵀ, A·V)

Attention is the trickiest but still manageable.

#### Q · Kᵀ – Similarity Scores

Given:

- Q: [T × d]  
- K: [T × d]  

We compute approximate similarity:

1. **Tile Partitioning:**
   - Each tile handles a subset of time steps (tokens) or heads  
   - Q and K slices for that head are loaded into LSP  

2. **Loop:**
   - For a query token qᵢ:
     - Load qᵢ into VIRF  
     - For each key token kⱼ:
       - Load kⱼ into VIRF / or stream  
       - Use additive approximation:
         - e.g. `s_ij ≈ sum( LUT(sign(qᵢ_k * kⱼ_k_code)) )` or  
         - `s_ij ≈ f(qᵢ + kⱼ)` with LUT scoring  
       - ACC accumulates similarity score  

3. **Normalize:**
   - Scores go through ASLUT (attention score LUT)  
   - approximate softmax / logit scale via table  

4. **Store attention weights aᵢⱼ in LSP/G-SRAM**

#### A · V – Weighted Sum

After we have attention weights:

1. Load attention rows aᵢ: [T]  
2. Load V: [T × d] (tiled)  
3. Use Adder Blocks to compute:
   - `oᵢ = Σⱼ aᵢⱼ · vⱼ`  
   - again with LUT for scaled addition instead of full multiplication  

---

### 4.4 Memory Access Optimization Techniques

To keep energy low:

1. **Weight Reuse**  
   - Store weights in G-SRAM compressed  
   - Decompress / decode per tile in small blocks  
   - Reuse across many tokens before evicting

2. **Activation Blocking**  
   - Split sequence dimension into manageable tiles  
   - Minimize re-reading the same activations from G-SRAM  

3. **Double Buffering in LSP**  
   - While computing on block A, prefetch block B  
   - Overlap compute and memory transfers  

4. **Broadcast Path**  
   - For x vectors shared across many outputs (dense layers), broadcast from G-SRAM to all tiles simultaneously

## 5. Control & Instruction Model

### 5.1 RISC-V Control Core

- Handles:
  - High-level orchestration (load model, schedule layers, I/O)  
  - Coordination between tiles  
  - Communication with external CPU / host  

### 5.2 Tile Microcode

Each tile has a **small instruction buffer** for micro-ops, e.g.:

- `LOAD_ACT src_addr, dst_reg`  
- `LOAD_WCODE src_addr, dst_reg`  
- `LUT_W dst_reg, src_reg`  
- `ADD_ACC acc_id, src_reg`  
- `CLIP_STORE acc_id, dst_addr`  
- `SYNC` (barrier)  

This makes the hardware flexible enough to support:

- different architectures (Transformer, MLP, CNN-like)  
- different quantization schemes (binary/ternary/2–4 bit)

## 6. Example: End-to-End Execution of a Transformer Block

For **one Transformer block**:

1. **Input embedding**  
   - Tile reads token IDs → LUT (embedding table) → LSP  

2. **Add positional encoding**  
   - PELUT provides PE vectors  
   - Adder lanes do elementwise add  

3. **Self-attention**
   - Compute Q/K/V via additive dense layers  
   - Compute attention scores via Q·Kᵀ (approx)  
   - Apply softmax approx via ASLUT  
   - Compute output via A·V additive  

4. **FFN / MLP**
   - Two dense layers with nonlinearity via ALUT  
   - Add & Norm approximated via add + ALUT  

5. **Write output activations**  
   - Stored back to G-SRAM or streamed out

All steps use the **same primitive blocks**:
- Adder Block  
- LUT Block  
- Local Scratchpad + Global SRAM
