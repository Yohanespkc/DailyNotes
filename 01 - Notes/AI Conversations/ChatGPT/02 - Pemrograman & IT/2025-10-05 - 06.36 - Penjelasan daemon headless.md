# 💬 Penjelasan daemon headless

**Tanggal:** `2025-10-05 06.36`

### 👤 User:
apa itu daemon headless

### 🤖 ChatGPT:
“Daemon headless” = layanan/proses latar belakang (daemon) yang berjalan **tanpa antarmuka grafis (GUI) dan tanpa TTY**. Ia start otomatis, tetap hidup meski Anda logout, dan dioperasikan lewat berkas konfigurasi, port jaringan, atau perintah kontrol—bukan lewat jendela aplikasi.

## Kenapa dipakai
- Hemat sumber daya & stabil untuk server/kontainer.
- Lebih aman (tak ada permukaan GUI).
- Cocok untuk otomasi & kerja jarak jauh (SSH, API).

## Contoh
- **sshd**, **nginx**, **cron**, **redis**, **postgres** (semuanya headless).
- **Headless Chrome** untuk scraping/tes otomatis (tanpa membuka browser).
- **Jupyter server** dengan `--no-browser` (menghidangkan UI via web, bukan jendela lokal).

## Cara menjalankan/menjaga (ringkas)
**Linux (systemd)**
```ini
# /etc/systemd/system/myservice.service
[Unit]
Description=My Headless Daemon

[Service]
ExecStart=/usr/local/bin/my-app --flag
Restart=always
User=myuser
WorkingDirectory=/opt/my-app

[Install]
WantedBy=multi-user.target
```
Perintah: `sudo systemctl daemon-reload && sudo systemctl enable --now myservice`

**macOS (launchd)**
```xml
<!-- ~/Library/LaunchAgents/com.example.myapp.plist -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>com.example.myapp</string>
  <key>ProgramArguments</key>
  <array><string>/usr/local/bin/my-app</string><string>--flag</string></array>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>WorkingDirectory</key><string>/Users/me/MyApp</string>
  <key>StandardOutPath</key><string>/tmp/myapp.out</string>
  <key>StandardErrorPath</key><string>/tmp/myapp.err</string>
</dict></plist>
```
Perintah: `launchctl load ~/Library/LaunchAgents/com.example.myapp.plist && launchctl start com.example.myapp`

**Windows**
- Istilahnya **Windows Service**. Buat via `sc create ...` atau pakai alat seperti **NSSM** untuk membungkus program CLI jadi service.

## Ciri & praktik baik
- Tidak meminta input interaktif; semua lewat config/env.
- Logging ke file atau jurnal (systemd/launchd).
- Pastikan izin/akses file benar, set **WorkingDirectory**, dan jangan bergantung pada variabel GUI (mis. `DISPLAY`).

Kalau Anda mau, sebutkan proses/aplikasi yang ingin dijadikan headless daemon—aku bisa tuliskan file service/plist-nya siap pakai.

# 1) Proses & batas aman (headless)
- **Daemon** start saat boot, tak butuh TTY/GUI. Kontrol via **CLI + API lokal** (Unix socket/localhost mTLS).
- Semua UI (Obsidian/Logseq/Web) hanyalah **klien** yang memanggil API; **data tetap di PKC**, bukan di plugin/UI.

```
[Obsidian] [Logseq] [Web UI] ──(mTLS+CapToken)──> [PKC Core Daemon]
                                              ├─ Identity & Keys (DID, HSM/Secure Enclave)
                                              ├─ Encrypted Store (files+vector DB)
                                              ├─ Capabilities (UCAN/Macaroon)
                                              ├─ Proxy Re-Encryption (PRE)
                                              ├─ Overlay VPN (WireGuard)
                                              ├─ Safe RAG/LLM (local)
                                              └─ WORM Audit Log (hash chain)
```

---

# 2) Identitas & kunci
- **Root identity**: DID + **root key** (sebaiknya di **Secure Enclave/TPM/HSM**).
- **Hierarki kunci**: kunci ruang/collection (**KEK**), kunci objek (**DEK**), kunci sesi (ephemeral).
- **Pairing multi-device**: perangkat baru diberi **capability minimal** + key derivation; **backup & recovery** via *Shamir secret sharing*.
- **Rotasi kunci** terjadwal; metadata tak sensitif tetap bisa dibaca (content tetap E2EE).

---

# 3) Penyimpanan terenkripsi (E2EE + versi)
- **Content-addressed** (mis. BLAKE3 CID), versi otomatis, deduplikasi.
- **Envelope encryption**: data dienkripsi **DEK**, DEK dibungkus **KEK** ruang. KEK diikat ke identitas pemilik.
- **Index vektor** (untuk RAG) disimpan terenkripsi; embedding **tidak** dibiarkan plaintext di disk.
- **Zero-trust**: plugin/UI tidak pernah memegang KEK/DEK; semua dekripsi terjadi di daemon.

Contoh konfigurasi ringkas:
```yaml
storage:
  root: /var/lib/pkc
  cipher: aes-256-gcm
  hash: blake3
  envelope: kek-per-space
identity:
  did_method: did:key
  keystore: secure-enclave
backup:
  shard: 5
  threshold: 3
```

---

# 4) Izin berbasis kapabilitas (Object-Capability)
- Gunakan **UCAN**/**Macaroon**: token kapabilitas memuat **siapa bisa apa atas apa** (+ *caveat* waktu, kuota, path).
- Beda dengan ACL klasik: **least-privilege by default**, bisa **delegasi granular** dan **dicabut**.
  
Contoh token (disederhanakan):
```json
{
  "iss":"did:key:zAlice", "aud":"did:key:zPluginObsidian",
  "att":[{"with":"pkc:space:research","can":["read","query"]}],
  "exp": 1767225600, "nbf": 1764624000, "caveats": {"path_prefix":"/notes"}
}
```

---

# 5) Berbagi via **Proxy Re-Encryption (PRE)**
- Data disimpan E2EE dengan DEK milik Anda. Saat berbagi:
  1) Anda menerbitkan **kebijakan** “koleksi X → Bob”.
  2) PKC membuat **re-encryption key** (RK) *owner→Bob* (contoh skema: **Umbral**).
  3) **Proxy** (boleh daemon Anda sendiri atau node tepercaya) **meng-re-encrypt** **DEK** → kunci publik Bob **tanpa** melihat plaintext.
  4) Bob mendekripsi data dengan private key-nya; **tanpa re-upload** atau share kunci master.
- Cabut akses = hapus kebijakan + rotasi KEK ruang (opsional per-file jika granular).

---

# 6) Overlay VPN (mesh pribadi antar-PKC)
- **WireGuard** P2P; peta **DID ↔ WG public key** disimpan di PKC.
- **Rendezvous** (STUN/TURN/self-host) untuk NAT traversal; kebijakan akses via kapabilitas.
- Hanya node berkapabilitas yang bisa **dial** ke koleksi/layanan tertentu; lalu lintas **E2EE**.

---

# 7) **RAG/LLM aman** (lokal & tak bocor)
Pipeline:
1) **Ingest** sumber (file, email, web snapshot) → normalisasi → PII redaction opsional (lokal).
2) **Embed** lokal (mis. llama.cpp/text-embeddings) → simpan **vektor terenkripsi**.
3) **Retrieve** berdasar kapabilitas caller; hasil didekripsi **sementara di memori**.
4) **Generate**: model **lokal terlebih dulu**. Jika perlu *remote model*, gunakan **guard-proxy**:
   - Hanya **ringkasan/fitur** yang keluar,
   - **Tak ada** DEK/identitas/konten mentah,
   - **Policy-as-code** (OPA/Rego) menolak prompt berisiko.
5) **Scrub** memori & log; hanya **hash CID** yang masuk audit.

Hasilnya: Anda dapat Chat/RAG di Obsidian/Logseq/web **tanpa** risiko eksfiltrasi konten PKC.

---

# 8) Audit **WORM** (Write-Once, Read-Many)
- Setiap aksi (“read X”, “re-encrypt Y”, “issue capability Z”) → **entry append-only**:
  - `hash_prev`, `timestamp`, `actor_did`, `cap_id`, `resource_cid`, `op`.
- **Hash chain/Merkle root** berkala; opsional **anchor** root ke media eksternal (email/timestamp service).
- Audit bisa dibaca, **tak bisa diubah**; cocok untuk kepatuhan/forensik.

---

# 9) API untuk UI & layanan
- **Transport**: gRPC/HTTP2 via **Unix socket** atau `127.0.0.1` mTLS.
- **Auth**: mTLS + **Capability token** pada header.
- **Event**: SSE/pubsub (mis. NATS lokal).

Contoh endpoint (ilustrasi):
```
POST /v1/store/put        # simpan file/objek
GET  /v1/store/get?cid=…  # ambil objek (butuh cap read)
POST /v1/rag/embed        # embed dokumen
POST /v1/rag/query        # query RAG
POST /v1/cap/issue        # terbitkan kapabilitas
POST /v1/share/policy     # atur kebijakan PRE
POST /v1/vpn/peer         # tambah peer WireGuard
GET  /v1/audit/stream     # stream log WORM
```

**Adapter UI**:
- **Obsidian/Logseq plugin**: sinkronisasi folder → PKC; semua operasi lewat API (cap: read/query/write subset).
- **Web UI**: halaman lokal untuk search/chat RAG, manajemen share, audit viewer.
- **Email bridge**: IMAP fetch → dekrip PGP/S/MIME (jika ada) → simpan + index terenkripsi; SMTP kirim via PKC (opsi sign/encrypt).

---

# 10) Kolaborasi & federasi (sovereign-by-design)
- **Spaces** berbasis **CRDT** (mis. Automerge) → edit offline, **merge tanpa konflik**.
- Sinkronisasi di atas **overlay VPN**; berbagi kunci via **PRE**.
- **Federasi**: discovery antar-DID, handshake kapabilitas, lalu tukar data terenkripsi; **tidak perlu server pusat**—boleh ada *coord server* opsional untuk rendezvous/metadata non-sensitif.

### 🤖 ChatGPT:
TTY = **teletype/terminal** di dunia Unix. Praktisnya, itu **antarmuka teks interaktif** yang menghubungkan program ke pengguna (stdin/stdout/stderr). Dulu perangkat fisik (teletype), sekarang bisa berupa jendela terminal, SSH, atau konsol virtual.

# Intinya
- **Ada TTY** → proses bisa berinteraksi: minta password, baca input, cetak ke layar.
- **Tidak ada TTY** → proses berjalan non-interaktif (cron, systemd, daemon headless, pipeline).

# Istilah yang sering muncul
- **/dev/tty**: “terminal pengendali” *saat ini* untuk proses.
- **/dev/tty1…**: konsol virtual (Ctrl+Alt+F1–F6 di Linux).
- **/dev/pts/N** (**PTY**): *pseudo-terminal*—yang Anda pakai di tab Terminal/SSH.
- **/dev/ttyS0**: serial TTY (UART/COM).

# Cek & trik cepat
```bash
tty               # lihat terminal yang dipakai, atau "not a tty"
ps -o pid,tty,cmd # kolom TTY setiap proses
[ -t 0 ] && echo "stdin TTY" || echo "stdin bukan TTY"
ssh -t host cmd   # paksa alokasi TTY
ssh -T host cmd   # jangan alokasikan TTY (non-interaktif)
docker run -it …  # -t = TTY, -i = keep stdin
```

# Kenapa penting
- Banyak program **butuh TTY** untuk prompt (sudo, passwd, top).
- **Daemon headless** sengaja dijalankan **tanpa TTY** agar stabil/otomatis.
- Skrip berperilaku beda jika input **bukan TTY** (mis. saat dipipe dari file).

apa maksud kalimat ini: semua pemrosesan AI terjadi di enclave/TEE (trusted execution environment) yang ter-attest

### 🤖 ChatGPT:
Intinya begini:

**Kalimat itu berarti**: semua komputasi AI (embedding, retrieval, inferensi LLM, dsb.) dijalankan **di dalam “kotak aman” hardware** bernama **enclave/TEE**. Kotak ini **mengisolasi kode & data** dari OS, hypervisor, bahkan admin root. Sebelum dipakai, kotak itu **membuktikan dirinya** lewat **attestation**—sebuah bukti kriptografis yang menyatakan *“aku benar-benar TEE asli, menjalankan kode versi X, di hardware Y”*. Setelah bukti ini **divalidasi**, barulah kunci/akses diberikan.

# Istilah kunci
- **TEE/Enclave**: lingkungan eksekusi terisolasi di CPU (contoh: Intel SGX, AMD SEV-SNP, ARM TrustZone/CCA, Apple Secure Enclave). Memori enclave dienkripsi & diproteksi.
- **(Remote) Attestation**: TEE menghasilkan **measurement** (hash kode + konfigurasi) dan **laporan/quote** yang **ditandatangani** root-of-trust hardware. Pihak luar memverifikasi tanda tangan dan mencocokkan hash yang diizinkan.

# Alur sederhananya
1) Daemon/servis AI start di dalam TEE → menghasilkan **attestation report**.  
2) PKC/Key Server memverifikasi: “signature valid, measurement = yang di-whitelist?”.  
3) Jika lolos, **kunci dekripsi/kapabilitas** dikirim **hanya** ke sesi TEE itu.  
4) Data terenkripsi didekripsi **di dalam TEE**, inferensi RAG/LLM berjalan di sana.  
5) Hasil (ringkasan/jawaban) keluar; kunci & plaintext **tak pernah keluar** dari enclave.

```
[Client/UI]
   │  (minta inferensi)
   ▼
[PKC Core]──verif attestation──┐
   │                            │ OK → rilis kunci/session cap
   ▼                            │
[TEE/Enclave: AI Engine] ◄──────┘
   │ (proses data rahasia di dalam)
   ▼
[Jawaban keluar tanpa bocor kunci]
```

# Apa yang dijamin
- **Kerahasiaan**: data & model rahasia hanya terlihat di dalam TEE.
- **Integritas**: Anda yakin **kode yang benar** yang berjalan.
- **Verifiabilitas**: ada bukti kriptografis *di mana & bagaimana* komputasi terjadi.

# Contoh kebijakan (gagasan)
```yaml
allow_inference_if:
  tee_vendor: ["intel-sgx","amd-sev-snp","arm-cca"]
  measurement_whitelist:
    - "b6c2…9af"   # hash binary AI build 1.3.2
  build_min_version: "1.3.0"
on_verify_success:
  issue_capability: "rag:infer:space/research"
  unwrap_keys: ["DEK:research"]
```

# Keterbatasan & kewaspadaan
- **Side-channel & I/O**: TEE tidak otomatis cegah kebocoran via pola waktu/ukuran atau log yang ceroboh—perlu hardening.
- **Ukuran memori/performansi**: enclave sering **lebih kecil** & ada overhead.
- **Supply-chain**: Anda tetap harus percaya pada vendor CPU & rantai build Anda.
- **Kebijakan keluar**: pastikan yang keluar dari TEE hanya **hasil minimal** (mis. ringkasan, bukan dokumen mentah).

# Analogi cepat
Bayangkan **brankas transparan kriptografis**: Anda bisa membuktikan brankas itu asli dan berisikan mesin AI versi yang Anda setujui. Anda memasukkan data & kunci ke brankas **hanya setelah** validasi keasliannya. Mesin bekerja di dalam; yang keluar cuma hasilnya.

Jika mau, saya bisa bantu susun **policy lengkap attestation → key-release** untuk PKC Core (mapping ke SGX/SEV/TrustZone) plus checklist hardening praktis.

### 🤖 ChatGPT:
Kalimat itu menggambarkan **dua lapisan keamanan penting** dalam arsitektur AI modern — satu di **tingkat jaringan (DPU)**, satu di **tingkat kecerdasan (LLM)**. Mari kita uraikan dengan analogi sederhana dan kemudian secara teknis.

## 🧩 Makna Umum

> **“Jaringan terenkripsi/tersegmentasi oleh DPU”**  
→ artinya **seluruh lalu lintas data antar server, node, atau chip AI** diamankan dan dipisahkan oleh **DPU (Data Processing Unit)** — sebuah prosesor khusus keamanan dan jaringan.  
DPU ini memastikan bahwa **hanya koneksi yang sah** (dengan kunci & kebijakan tertentu) yang bisa lewat, dan semua data di jalur itu **dienkripsi secara real-time**.

> **“LLM dibungkus guardrails + DLP”**  
→ artinya **model bahasa (LLM)** tidak berdiri bebas, tetapi dijalankan di dalam **pembungkus keamanan (guardrails)** yang:
- memfilter atau menolak pertanyaan/jawaban yang berisiko,
- memeriksa konten yang keluar dengan **DLP (Data Loss Prevention)** untuk mencegah **kebocoran data sensitif** seperti nama pribadi, NIK, rahasia proyek, dsb.

Dengan kombinasi ini, **baik data di jaringan maupun hasil AI** dijaga agar **tidak bocor, tidak salah arah, dan tidak keluar dari konteks izin.**

## ⚙️ Lapisan 1 — Jaringan terenkripsi & tersegmentasi oleh DPU

### 🔒 Arti teknis
- **DPU (Data Processing Unit)** adalah chip tambahan (mis. NVIDIA BlueField, Intel IPU, AWS Nitro) yang duduk di antara **CPU/GPU ↔ jaringan**.  
- Ia melakukan enkripsi, firewall, routing, dan isolasi **langsung di hardware**, bukan di OS.

### 🔧 Fungsinya
1. **Segregasi trafik** antar zona (mis. RAG node, storage node, enclave node).  
2. **Inline encryption**: setiap paket dienkripsi di DPU (TLS/IPsec/WireGuard inline).  
3. **Zero-trust segmentation**: setiap aplikasi/node punya identitas & policy sendiri.  
4. **Offload CPU**: beban kriptografi & I/O dipindah ke DPU → CPU/GPU fokus ke AI.

### 💡 Contoh
```
[LLM Node]───DPU───(encrypted segment A)───[Storage Node]
                    (encrypted segment B)───[VPN Gateway]
```
Masing-masing “segment” punya aturan sendiri (mis. hanya model tertentu boleh baca dataset tertentu).

## 🧠 Lapisan 2 — LLM dibungkus guardrails + DLP

### 🛡️ Guardrails
Lapisan logika yang **menyaring prompt & respons** sebelum dan sesudah masuk ke model.  
Contoh mekanisme:
- Filter prompt berbahaya (“bocorkan password admin”).
- Validasi konteks: hanya pertanyaan tentang dataset yang diizinkan.
- Limitasi panjang output, tipe data, atau format.
- Logging & audit setiap interaksi.

### 🧯 DLP (Data Loss Prevention)
Mekanisme untuk **mendeteksi & memblokir** jika model mencoba mengeluarkan:
- Data pribadi (nama, alamat, NIK),
- Dokumen rahasia internal,
- Kunci API, password, token,
- Informasi klasifikasi tinggi (Confidential, Secret, dll).

Biasanya berbentuk **pattern matcher + AI detector + policy**.

### 💡 Contoh
```
User Prompt
   ↓
[Guardrails Layer]
   - periksa niat, izin, konteks
   ↓
[LLM Engine]
   ↓
[DLP Layer]
   - redaksi / blok output sensitif
   ↓
User
```

Jika model mencoba menjawab:
> “Berikan isi dokumen rahasia proyek X”

Maka guardrails akan memblok atau mengganti dengan:
> “Maaf, saya tidak dapat menampilkan informasi rahasia.”

## 🧩 Arti singkat
`stdin`, `stdout`, dan `stderr` adalah **tiga aliran data standar (standard streams)** yang dimiliki setiap proses di sistem seperti **Linux, macOS, atau Windows**.

| Nama | Singkatan | Arah | Fungsinya |
|------|------------|------|------------|
| **stdin** | *standard input* | masuk ke program | tempat program menerima data (biasanya dari keyboard, file, atau pipe) |
| **stdout** | *standard output* | keluar dari program | tempat program menulis hasil (biasanya ke layar atau ke file) |
| **stderr** | *standard error* | keluar dari program | tempat program menulis pesan kesalahan atau log |

---

## 📊 Ilustrasi sederhana
Bayangkan kamu jalankan ini di terminal:

```bash
cat file.txt
```

- **stdin**: kosong (tidak ada input dari keyboard atau pipe)  
- **stdout**: isi `file.txt` dikirim ke layar  
- **stderr**: jika file tidak ada, error-nya muncul di layar juga  

---

## ⚙️ Contoh praktis

### 1️⃣ Mengirim input via `stdin`
```bash
echo "halo" | tr a-z A-Z
```
- `echo "halo"` menulis ke **stdout**  
- tanda `|` (pipe) mengalihkan **stdout** dari `echo` menjadi **stdin** untuk `tr`  
- hasil: `HALO`

---

### 2️⃣ Mengalihkan `stdout` ke file
```bash
ls > daftar.txt
```
- `>` berarti **redirect stdout** ke file  
- hasil `ls` masuk ke `daftar.txt`, bukan layar  

---

### 3️⃣ Mengalihkan `stderr` ke file
```bash
ls /folder/tidak/ada 2> error.log
```
- `2>` artinya **redirect file descriptor 2** (yaitu `stderr`)  
- pesan kesalahan disimpan di `error.log`, bukan di layar  

---

### 4️⃣ Mengalihkan keduanya
```bash
ls / > output.log 2>&1
```
- `>` kirim **stdout** ke `output.log`  
- `2>&1` artinya kirim **stderr** ke tempat yang sama dengan **stdout**

## 🧠 Konteks dulu: Apa itu *Embedding* dan *RAG*?

### 🔹 **Embedding**
- “Embedding” = representasi angka (vektor) dari teks, gambar, atau data lain.  
- Misalnya kalimat **“Matematika Gasing itu asyik”** diubah oleh model AI jadi vektor seperti:
  ```
  [0.12, -0.83, 0.47, ...]
  ```
- Vektor inilah yang dipakai mesin untuk **mengukur kemiripan makna** antar teks.

Contoh:
- “Matematika Gasing itu asyik” dan “Belajar Gasing menyenangkan” akan punya vektor yang mirip.

---

### 🔹 **RAG (Retrieval-Augmented Generation)**
- RAG = teknik di mana sebelum LLM menjawab pertanyaan, sistem **mengambil (retrieve)** informasi relevan dari database atau dokumen yang disimpan sebelumnya (berdasarkan embedding).  
- Jadi LLM tidak mengandalkan hafalan, tapi **“membaca dulu” dokumen terkait**.

Alurnya kira-kira begini:
```
Pertanyaan user → ubah jadi embedding → cari teks paling mirip di database → 
gabungkan hasilnya → kirim ke LLM → LLM menjawab dengan konteks tambahan.
```

## ⚙️ Sekarang: “Redis jadi cache embedding & RAG” artinya apa?

Redis (sebagai in-memory database) digunakan untuk **menyimpan hasil embedding dan hasil retrieval sementara** agar sistem RAG bisa **lebih cepat dan hemat energi**.

Mari kita pecah 👇  

### 1️⃣ **Cache embedding**
- Membuat embedding itu mahal (butuh model & komputasi).  
- Jadi setiap kali teks atau dokumen sudah di-embed, hasilnya disimpan di **Redis** agar tidak perlu dihitung ulang.

Contoh alur:
```
Teks: "Belajar Gasing menyenangkan"
↓
embedding model menghasilkan vektor [0.12, -0.83, ...]
↓
Redis.store("embedding:Belajar Gasing menyenangkan", [0.12, -0.83, ...])
```
Lain kali, jika teks yang sama diproses lagi, sistem cukup ambil hasilnya dari Redis — **tidak perlu menjalankan model lagi.**

---

### 2️⃣ **Cache RAG**
- Saat pengguna bertanya hal yang sama atau mirip, hasil pencarian (retrieval) atau bahkan hasil jawaban bisa **disimpan sementara di Redis**.

Contoh:
```
Pertanyaan: “Apa itu Metode Gasing?”
→ sistem cari dokumen relevan + buat jawaban

Redis.store("rag:Apa itu Metode Gasing?", "Metode Gasing adalah ...")

```

Jika nanti ada pengguna lain menanyakan pertanyaan yang **mirip**, sistem bisa:
- Ambil dulu hasil dari Redis (cepat),
- Kalau ada perubahan pada data terbaru → update cache-nya.

## ⚡ Keuntungan pakai Redis untuk cache embedding & RAG
| Keuntungan | Penjelasan |
|-------------|-------------|
| **Kecepatan tinggi** | Redis bekerja di memori (RAM), jauh lebih cepat daripada baca dari disk/database besar. |
| **Mengurangi biaya AI** | Tidak perlu menghitung embedding berulang-ulang. |
| **Skalabilitas** | Banyak node RAG bisa pakai Redis sebagai cache bersama. |
| **Fault tolerance** | Jika node RAG mati, embedding-nya tetap bisa diambil dari cache Redis. |

> 🔹 M-Card = memori jangka panjang (pengetahuan yang terstruktur)

---

## 🧩 5️⃣  Hubungan dalam PKC Core

Dalam **arsitektur PKC Core**, urutannya kira-kira begini:

```
Dokumen / Data mentah
        ↓
Embedding (LLM encoder)
        ↓
Cache Redis (hasil embedding)
        ↓
RAG Retrieval (pakai cache)
        ↓
LLM reasoning (jawaban awal)
        ↓
Evaluator + Validator
        ↓
Disimpan sebagai M-Card (pengetahuan terverifikasi)
```

Jadi:
- Cache Redis membantu sistem **berpikir cepat**.  
- M-Card membantu sistem **berpikir cerdas dan teringat lama.**

- **DID (Decentralized Identifier):** identitas kriptografis (contoh: `did:key:z...`) untuk manusia/perangkat/ruang data.
- **HSM/Secure Enclave/TPM:** tempat aman untuk menyimpan kunci akar (root key) & melakukan operasi kripto **tanpa** mengekspos kunci mentah ke RAM.
- **Hierarki kunci:** KEK (kunci ruang) membungkus DEK (kunci objek), plus kunci sesi (ephemeral) untuk performa.

- **Teknik:** *envelope encryption* (data dienkripsi DEK; DEK dibungkus KEK ruang), *content-addressed* (CID/hash BLAKE3) + versi/deduplikasi.

# 5) Proxy Re-Encryption (PRE)
- **Masalah yang diselesaikan:** Berbagi E2EE tanpa memberikan kunci master dan tanpa re-upload.
- **Cara kerja ringkas:**
  1) Data terenkripsi dengan DEK milik pemilik.
  2) Pemilik menerbitkan kebijakan berbagi ke penerima.
  3) PKC menghasilkan **re-encryption key (RK)** owner→penerima (skema mis. Umbral).
  4) Proxy mengubah **bungkus kunci** (bukan plaintext data) sehingga penerima dapat mendekripsi pakai kunci privatnya.
- **Cabut akses:** hapus kebijakan + (opsional) rotasi KEK/DEK ruang/objek.

# 6) Overlay VPN (WireGuard)
- **Apa ini?** Jaringan privat terenkripsi antar node PKC (HP, mini-PC, server).
- **Identitas jaringan:** kunci publik WireGuard dipetakan ke DID.
- **Fungsi:** segmentasi layanan (mis. hanya node tertentu bisa mengakses ruang data tertentu), NAT traversal via STUN/TURN, *zero-trust* antar perangkat.
- **Hasil:** ribuan PKC dapat berkolaborasi sebagai *mesh* tanpa DC pusat.

# 7) Safe RAG/LLM (local)
- **Pipeline aman**: ingest → redaksi opsional → embed lokal → simpan vektor terenkripsi → retrieve sesuai kapabilitas → generate (model lokal terlebih dulu).
- **Pembatas kebocoran:** guardrails + DLP (deteksi PII/rahasia), kebijakan *allowlist* sumber, serta (opsional) eksekusi di TEE/enclave ter-attest.
- **Tujuan:** Jawaban kaya konteks **tanpa** mengekspor dokumen mentah atau kunci keluar dari PKC.

# 8) WORM Audit Log (hash chain)
- **WORM (Write Once, Read Many):** log tak bisa diubah; setiap entri mengandung `prev_hash`, `timestamp`, `actor_did`, `cap_id`, `resource_cid`, `op`.
- **Hash chain/Merkle root:** memudahkan verifikasi integritas & *anchoring* berkala (opsional) ke sumber eksternal.
- **Manfaat:** jejak forensik & kepatuhan—“siapa mengakses apa, kapan, pakai izin apa”.

## 🧠 1️⃣ Pengertian singkat

**TLS (Transport Layer Security)** adalah **protokol keamanan** yang:
> melindungi data yang dikirim melalui jaringan agar **tidak bisa disadap, dimodifikasi, atau dipalsukan**.

TLS bekerja di antara **aplikasi (misalnya browser)** dan **transport (TCP/IP)** — makanya disebut “transport layer”.

---

## 🔐 2️⃣ Tujuan utama TLS

| Tujuan | Artinya |
|--------|----------|
| **Enkripsi** | Semua data diubah menjadi bentuk acak supaya tidak bisa dibaca penyadap. |
| **Integritas** | Menjamin data tidak diubah di tengah jalan. |
| **Autentikasi** | Memastikan kamu benar-benar terhubung ke server yang asli (bukan penyamar). |

---

## 🧩 3️⃣ Contoh paling mudah

Ketika kamu buka situs ini:

```
https://example.com
```

Huruf **“s”** pada `https` berarti **HTTP over TLS**.

Browser dan server melakukan proses yang disebut **TLS handshake**, lalu:
1. Menyepakati versi TLS dan algoritma enkripsi yang digunakan.  
2. Server mengirim **sertifikat digital** (biasanya dari *Certificate Authority*, CA).  
3. Browser memverifikasi sertifikat itu benar dan cocok dengan domain.  
4. Keduanya membuat **session key rahasia** untuk mengenkripsi komunikasi berikutnya.

Setelah handshake selesai:
- Semua data dikirim terenkripsi.  
- Pihak ketiga tidak bisa melihat isi permintaan maupun jawaban.

---

## ⚙️ 4️⃣ Sedikit teknis (tapi ringkas)

### Handshake sederhana
```
ClientHello  →  versi TLS, cipher suite
ServerHello  →  pilih cipher, kirim sertifikat
Client ↔ Server → tukar kunci (Diffie–Hellman)
Semua pesan berikutnya → dienkripsi dengan session key
```

### Algoritma umum
- **RSA / ECDHE** untuk pertukaran kunci  
- **AES / ChaCha20** untuk enkripsi data  
- **SHA256 / SHA384** untuk integritas (MAC/HMAC)

---

## 🔒 5️⃣ Hubungan dengan HTTPS, SSH, dan mTLS

| Protokol | Pakai TLS? | Keterangan |
|-----------|-------------|------------|
| **HTTPS** | ✅ Ya | HTTP + TLS (komunikasi web aman) |
| **FTPS / SMTPS** | ✅ Ya | Versi aman FTP & email |
| **SSH** | ❌ Tidak (pakai protokol sendiri) | Serupa tapi bukan TLS |
| **mTLS (mutual TLS)** | ✅ Ya (dua arah) | Klien **juga** punya sertifikat, jadi keduanya saling autentikasi |

## 🪪 2️⃣ **Identity (DID = Decentralized Identifier)**

### 🔍 Apa itu DID
**DID (Decentralized Identifier)** adalah **identitas digital yang tidak tergantung pada server pusat** (seperti Google, Facebook, atau pemerintah).  
Ia berbentuk seperti:
```
did:key:z6Mkh4nQ2x...  
did:web:example.com  
did:pkc:node123
```

Setiap **DID** punya pasangan:
- **Kunci publik** → digunakan orang lain untuk memverifikasi tanda tanganmu.  
- **Kunci privat** → hanya kamu yang punya, untuk menandatangani atau mendekripsi.

Contoh analogi:
> Kalau alamat rumah = nama DID,  
> maka kunci rumah = kunci privat.  

---

### 💡 Fungsi utama DID dalam PKC
| Fungsi | Penjelasan |
|---------|-------------|
| **Identitas unik** | Membedakan setiap node, pengguna, atau perangkat tanpa server pusat. |
| **Otentikasi aman** | Verifikasi antar node dilakukan dengan tanda tangan digital. |
| **Delegasi & reputasi** | Setiap identitas bisa punya kapabilitas dan catatan audit sendiri. |

Contoh:  
`did:pkc:lab-bali` = laboratorium rahasia di Bali  
`did:pkc:fajar` = user bernama Pak Fajar  

Keduanya bisa berinteraksi tanpa server pusat, hanya lewat pertukaran tanda tangan & kunci publik.

---

## 🔑 3️⃣ **Keys (Kunci Kriptografi)**

Setiap DID dikendalikan oleh **pasangan kunci (key pair):**
- **Private key (rahasia)** → dipakai untuk menandatangani dan mendekripsi.  
- **Public key (terbuka)** → digunakan oleh orang lain untuk memverifikasi dan mengenkripsi untukmu.

Biasanya menggunakan algoritma seperti:
- **Ed25519 / X25519**
- **ECDSA (secp256k1)**
- **RSA 4096**

---

## 🧱 4️⃣ **HSM / Secure Enclave**

Nah, inilah bagian **hardware** yang memastikan kunci-kunci itu **tidak pernah bocor ke luar.**

### 🔹 HSM (Hardware Security Module)
- Perangkat keras khusus (server-class) untuk **menyimpan dan mengelola kunci kriptografi**.  
- Kunci privat **tidak pernah keluar** dari chip — semua tanda tangan & dekripsi dilakukan *di dalam HSM*.
- Digunakan di bank, data center, dan sistem yang butuh jaminan keamanan tinggi.

### 🔹 Secure Enclave / TPM / TrustZone
- Versi ringan di perangkat pribadi (laptop, HP, SoC).  
- Apple punya **Secure Enclave**, Intel punya **SGX**, ARM punya **TrustZone**, PC punya **TPM**.
- Mereka membuat “ruang aman” dalam CPU tempat operasi kripto dilakukan.

### 🔐 Contoh proses
Ketika PKC Core butuh menandatangani pesan:
1. Daemon memanggil **Secure Enclave** untuk menandatangani hash.  
2. Kunci privat **tidak pernah keluar** ke memori biasa.  
3. Hasil tanda tangan dikirim keluar, bukan kuncinya.

---

## 🧠 5️⃣ Kenapa ini penting

| Masalah tanpa sistem ini | Solusi dengan DID + HSM/Secure Enclave |
|---------------------------|----------------------------------------|
| Identitas mudah dipalsukan | Setiap identitas punya kunci publik unik yang diverifikasi kriptografi. |
| Password bisa dicuri | Tidak ada password—akses berbasis kunci digital. |
| Kunci bisa bocor dari RAM | Kunci disimpan di enclave/HSM, tak bisa diambil bahkan oleh root. |
| Data antar node mudah disadap | Setiap pesan ditandatangani & dienkripsi per identitas. |

- `backup` → jika perangkat hilang, kunci bisa dipulihkan dari 3 dari 5 potongan (Shamir secret sharing).

## 🧠 1️⃣ Apa itu *Encrypted Store (files + vector DB)*  

**Encrypted Store** artinya **tempat penyimpanan data yang terenkripsi ujung-ke-ujung (end-to-end encrypted)**.  
Data di sini tidak pernah disimpan dalam bentuk asli (plaintext), bahkan **PKC Core sendiri tidak tahu isi datanya** tanpa kunci yang tepat.  

Ia terdiri dari dua bagian besar:

| Komponen | Fungsi |
|-----------|--------|
| **Files Store** | Menyimpan berkas mentah: dokumen, gambar, audio, M-Card, konfigurasi, dsb. |
| **Vector DB** | Menyimpan **embedding vektor** (hasil transformasi teks/gambar menjadi angka) untuk mendukung RAG, pencarian semantik, dan reasoning AI. |

---

## 🔐 2️⃣ Prinsip dasar: *Envelope Encryption*  

Setiap data terenkripsi menggunakan dua lapisan kunci:

```
Data → dienkripsi dengan DEK (Data Encryption Key)
DEK → dienkripsi dengan KEK (Key Encryption Key)
KEK → dipegang oleh ruang/identitas pemilik
```

Contoh struktur:

```
+--------------------------+
| File: laporan.pdf        |
|  ├── ciphertext (AES-GCM)|
|  └── header: {KEK_ID, DEK_encrypted} 
+--------------------------+
```

- **DEK** dibuat unik untuk setiap file atau objek (misalnya AES-256-GCM).  
- **KEK** adalah kunci ruang kerja atau identitas pemilik yang disimpan aman di HSM/Secure Enclave.  
- Saat file dibuka, hanya enclave yang mendekripsi DEK menggunakan KEK, lalu DEK mendekripsi data.

Hasilnya:  
> Walau seseorang mencuri seluruh storage, ia hanya mendapatkan *ciphertext* acak tanpa kunci.

## 🧩 3️⃣ Bagian A — **Files Store**

### a) Isi yang disimpan:
- Dokumen (`.md`, `.pdf`, `.docx`, `.csv`, dll)
- Catatan dari Obsidian / Logseq
- Hasil kerja AI (ringkasan, M-Card)
- Gambar, audio, video (opsional)
- Metadata terenkripsi (tanggal, hash, versi)

### b) Fitur utama:
| Fitur | Penjelasan |
|--------|-------------|
| **Content-addressed** | Setiap file diberi ID = hash isinya (mis. BLAKE3 CID). |
| **Versioned** | Setiap revisi disimpan seperti *Git commit*. |
| **Deduplication** | File identik hanya disimpan sekali. |
| **Compression + encryption** | Hemat ruang, aman. |
| **Searchable metadata** | Metadata ringan disimpan terenkripsi parsial (bisa cari tanpa membuka isi). |

### c) Lokasi fisik:
- Bisa di **disk lokal**, **server PKC**, atau **storage object** (MinIO, S3)  
- Tetapi **semuanya terenkripsi dari sisi klien** sebelum dikirim (client-side encryption).

---

## 🧮 4️⃣ Bagian B — **Vector DB**

### a) Fungsi:
Tempat menyimpan **embedding vektor** hasil pemrosesan AI (teks, gambar, audio, kode).  
Embedding ini memungkinkan sistem:
- mencari teks yang **bermakna serupa** meski beda kata,  
- menjalankan **RAG (Retrieval-Augmented Generation)**,  
- dan menghubungkan M-Card dengan konteks yang mirip.

### b) Contoh data:
| Dokumen | Embedding (disingkat) |
|----------|-----------------------|
| "Matematika Gasing itu mudah" | [0.11, -0.82, 0.54, ...] |
| "Cara cepat berhitung 7×8" | [0.09, -0.81, 0.52, ...] |

Embedding-embedding ini disimpan dalam **basis data vektor terenkripsi**, biasanya mendukung:
- **cosine / dot similarity search**  
- **filter berdasarkan kapabilitas**  
- **hasil retrieval terenkripsi** (hanya PKC dengan izin bisa dekripsi hasilnya)

### c) Keamanan:
- Embedding sendiri **juga terenkripsi (DEK-per-batch)**.  
- Untuk query, PKC Core mendekripsi embedding di memori enclave, bukan di disk.  
- Hasil similarity (jarak vektor) dikirim kembali ke modul **Safe RAG/LLM**.

## ⚙️ 5️⃣ Bagaimana data mengalir (alur nyata)

```
[Obsidian/Web UI]
       │ upload
       ▼
 ┌───────────────┐
 │ PKC Core API  │
 └──────┬────────┘
        │ 1. buat DEK unik
        │ 2. enkripsi data (AES-GCM)
        │ 3. bungkus DEK dengan KEK (RSA/EC)
        ▼
 [Encrypted Store]
    ├── files/
    ├── vectors/
    └── metadata/
```

Saat pengguna membaca kembali file:
1. Daemon verifikasi CapToken (izin).  
2. Ambil metadata & DEK terenkripsi.  
3. Dekripsi DEK menggunakan KEK di enclave.  
4. Gunakan DEK untuk membuka file dan kirim hasil ke UI.

## 🧰 6️⃣ Contoh konfigurasi (YAML)

```yaml
storage:
  root: /var/lib/pkc
  cipher: aes-256-gcm
  hash: blake3
  envelope: kek-per-space
  vectordb:
    type: sqlite-faiss
    encrypt: true
    metric: cosine
```

## 🧩 7️⃣ Hubungan dengan fitur lain PKC Core

| Modul lain | Hubungan dengan Encrypted Store |
|-------------|--------------------------------|
| **Identity & Keys** | Menyediakan KEK untuk enkripsi/dekripsi file dan embedding. |
| **Capabilities (UCAN)** | Mengontrol siapa bisa baca/tulis file tertentu. |
| **Proxy Re-Encryption (PRE)** | Memungkinkan berbagi file tanpa membocorkan KEK asli. |
| **Safe RAG/LLM** | Mengambil embedding dari Vector DB secara aman untuk reasoning. |
| **WORM Audit** | Mencatat setiap aktivitas baca/tulis/dekripsi. |

## 🧭 8️⃣ Analogi sederhana

Bayangkan PKC Core seperti **perpustakaan super aman**:

- **Lemari besi (Encrypted Store)** menyimpan semua buku & catatan.  
- Setiap buku dikunci dengan **kunci unik (DEK)**.  
- Kunci DEK itu sendiri dikunci lagi oleh **kunci ruang (KEK)** yang hanya kamu punya di **HSM/Enclave**.  
- Ada **rak rahasia (Vector DB)** yang menyimpan *peta konsep* dari isi buku (embedding), sehingga kamu bisa mencari “konsep yang mirip” tanpa membuka semua buku.  

---

## 🧩 9️⃣ Kesimpulan

> **Encrypted Store (files + vector DB)** adalah fondasi keamanan data di PKC Core:
> - Semua file & embedding disimpan **terenkripsi ujung-ke-ujung**.  
> - Tiap file punya **kunci unik (DEK)** yang dibungkus oleh **kunci ruang (KEK)** di enclave.  
> - **Vector DB** menyimpan embedding untuk pencarian cerdas dan RAG, juga terenkripsi.  
> - Tidak ada pihak lain — bahkan admin sistem — yang bisa membaca data tanpa kapabilitas dan kunci yang sah.
