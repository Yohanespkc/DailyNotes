 Saya perlu menjelaskan BMAD dan hubungannya dengan Antigravity dalam bahasa Indonesia dengan analogi sederhana yang mudah dipahami.## Apa itu BMAD?

BMAD adalah singkatan dari Breakthrough Method for Agile AI-Driven Development, sebuah kerangka kerja terstruktur yang membuat pengembangan software lebih cepat dan konsisten dengan memanfaatkan agen-agen AI yang terspesialisasi.

**Analogi sederhana:** bayangkan membangun rumah. Cara biasa pakai AI itu seperti menyuruh satu tukang serba bisa mengerjakan semuanya sambil ngobrol panjang. Lama-lama dia lupa instruksi awal, hasilnya tidak konsisten. BMAD seperti punya tim lengkap: ada arsitek, mandor, tukang bangunan, dan pengawas, masing-masing dengan tugas jelas dan dokumen tertulis sebagai pegangan bersama.

## Cara kerjanya

BMAD menyediakan 12+ agen spesialis seperti PM, Architect, Developer, dan UX, dengan alur kerja terstruktur yang mencakup analisis, perencanaan, arsitektur, hingga implementasi. Alurnya kira-kira begini:

1. **Analisis** → agen Analyst membantu menggali kebutuhan proyek
2. **Perencanaan** → agen PM menyusun PRD (dokumen kebutuhan produk)
3. **Arsitektur** → agen Architect mendesain struktur sistem
4. **Implementasi** → dokumen besar dipecah menjadi "story files" kecil dengan konteks terfokus, lalu agen spesialis mengerjakannya

Kuncinya: dokumentasi menjadi satu-satunya sumber kebenaran. Tanpa ini, kebanyakan kegagalan AI coding terjadi karena percakapan tidak terstruktur: konteks hilang setelah dua hari, asumsi menumpuk, dan AI berperilaku seperti rekan kerja yang berbeda setiap kali.

## Dengan Antigravity

Cara pakainya cukup sederhana:

1. Instal di folder proyek: `npx bmad-method install` (lewat terminal Antigravity)
2. Ikuti petunjuk installer, lalu buka AI IDE di folder proyek tersebut. Antigravity termasuk yang didukung karena BMAD pada dasarnya bekerja lewat file markdown berisi instruksi agen
3. Panggil agen sesuai fase: mulai dari Analyst untuk brainstorming, lanjut PM, Architect, lalu Developer
4. Setiap agen menulis hasilnya ke dokumen, sehingga agen berikutnya (atau sesi besok) tidak kehilangan konteks

**Untuk konteks AI Tutor GASING:** kerangka ini cocok karena proyeknya melibatkan banyak komponen (RAG, modelfile, integrasi game Unity). Misalnya, agen Architect bisa memegang dokumen arsitektur RAG yang konsisten, sementara agen Developer mengerjakan satu modelfile per "story" tanpa harus mengulang penjelasan keseluruhan sistem setiap kali.

Yang menarik, framework ini juga dipakai product manager dan analis untuk tugas di luar coding, karena intinya adalah memberi struktur pada pemecahan masalah kompleks. Jadi alur editorial buku 4 volume pun bisa dikelola dengan pola yang sama.

## 1. Selamatkan dulu versi yang sukses (kalau masih bisa)

Git menyimpan riwayat meski tampaknya hilang. Coba di terminal Antigravity:

```bash
git reflog
```

Ini menampilkan semua titik yang pernah ada, termasuk sebelum pull yang merusak. Cari baris saat game masih bagus, catat kodenya (misal `a1b2c3d`), lalu:

```bash
git checkout a1b2c3d -- path/ke/file/game
```

Ini mengembalikan **hanya file game** ke versi sukses, tanpa mengganggu yang lain.

## 2. Pasang "save point" supaya tidak terulang

Tiga kebiasaan ini menghentikan masalah Anda:

**a. Commit SEBELUM pull.** Jangan pernah `git pull` saat ada perubahan belum tersimpan. Simpan dulu:
```bash
git add .
git commit -m "Adventure game versi sukses"
```
Kalau pull merusak, Anda tinggal kembali ke commit ini.

**b. Tandai versi yang sukses dengan tag.** Begitu sebuah game berhasil:
```bash
git tag adventure-sukses-v1
```
Kapan pun rusak, `git reset --hard adventure-sukses-v1` mengembalikan semuanya.

**c. Jangan edit file yang sama dengan teman.** Bagi kepemilikan file. Anda pegang scene A, teman pegang scene B. Konflik Unity paling sering muncul karena dua orang menyentuh satu scene.

## 3. Khusus Unity: aktifkan merge yang aman

Buat file `.gitattributes` di root proyek berisi:
```
*.unity merge=unityyamlmerge
*.prefab merge=unityyamlmerge
*.asset merge=unityyamlmerge
```
Lalu di Unity: **Edit > Project Settings > Editor > Asset Serialization = Force Text**. Ini membuat file Unity bisa di-merge jauh lebih baik.

## 4. Sisi BMAD: kunci story yang sudah selesai

Di sinilah BMAD membantu agar Anda **tidak pernah mulai dari nol** lagi. Saat sebuah adventure game sukses, jangan biarkan spesifikasinya hanya di kepala atau di chat. Simpan sebagai story file yang ditandai "selesai/locked". Jadi seandainya file game benar-benar hilang, agen Developer punya cetak biru lengkap untuk membangun ulang dengan terpandu, bukan menebak dari awal.

Singkatnya: **git tag = save point Anda, BMAD story = cetak biru bangun ulang.** Dua-duanya membuat insiden git pull yang salah hanya jadi gangguan kecil, bukan kerja ulang berjam-jam.

## Langkah 3: Buat "papan klaim" sederhana

Sebelum mulai kerja, tulis di grup chat atau satu file teks bersama (misal `SIAPA-KERJA-APA.txt` di repo):


Sederhana, tapi ini menghentikan 90% konflik. Kalau teman mau buka Adventure3, dia lihat papan ini dulu dan menunggu.

## Langkah 4: Ritual git harian (wajib, urutannya penting)

**Pagi, sebelum mulai kerja:**
```bash
git pull
```
Tarik dulu pekerjaan teman SEBELUM Anda menyentuh apa pun. Saat ini aman karena belum ada perubahan Anda yang bisa bertabrakan.

**Sore, setelah selesai:**
```bash
git add .
git commit -m "Adventure3: selesai puzzle pintu"
git push
```
Simpan dan kirim ke teman di hari yang sama. Jangan menumpuk perubahan berhari-hari, makin lama makin besar risiko tabrakan.

Aturan emasnya: **pull di pagi hari, push di sore hari, dan jangan pernah pull saat ada perubahan belum di-commit.** Yang terakhir inilah yang merusak game Anda kemarin.

Ada satu kehalusan yang penting dan sering terlewat: yang nol hanyalah **kecepatannya**, bukan **percepatannya**. Titik kontak tetap punya percepatan sentripetal sebesar ω²R yang mengarah ke pusat cakram. Inilah sebabnya titik itu bisa diam sesaat namun tergantikan oleh titik material lain pada saat berikutnya. Titik kontak adalah titik geometris, bukan satu titik material yang tetap.

## Gaya gesek tidak melakukan usaha

Karena titik kontak diam, gaya gesek statis bekerja pada titik yang kecepatannya nol. Daya sesaatnya:

$$P = \vec{F}_{gesek} \cdot \vec{v}_{kontak} = \vec{F}_{gesek} \cdot 0 = 0$$

Jadi gaya gesek statis **tidak melakukan usaha** dan **tidak membuang energi** menjadi panas. Inilah bedanya dengan gesek kinetik (saat slip), yang melakukan usaha negatif dan mendisipasi energi.

Ada cara yang lebih kaya untuk melihat ini, yang mungkin Anda sukai untuk pengajaran. Misalkan gesek mengarah mundur sebesar F. Pisahkan kontribusinya menjadi dua bagian:

Bagian translasi: $\vec{F} \cdot \vec{v}_{pm} = -Fv$ (mengurangi energi kinetik translasi).

Bagian rotasi: $\tau \omega = (FR)\omega = +Fv$ (menambah energi kinetik rotasi, karena $v = R\omega$).

Jumlahnya: $-Fv + Fv = 0$. Jadi gesek tidak menghilangkan energi, melainkan hanya **memindahkannya** antara mode translasi dan rotasi. Net usahanya tetap nol. Ini intuisi yang bagus: gesek statis adalah "calo" energi, bukan "perampok" energi.

## Mengambil titik putar di titik kontak

Di sinilah hadiah eleganinya. Kalau Anda mengambil titik kontak sebagai poros untuk menghitung torsi, **dua gaya langsung hilang dari persamaan**:

Gaya gesek bekerja **tepat di** titik kontak, sehingga lengan momennya nol. Torsinya nol. Gaya normal juga bekerja di titik kontak (untuk kontak titik ideal), sehingga torsinya juga nol.

Yang tersisa hanya torsi dari gravitasi. Untuk cakram menggelinding menuruni bidang miring, ini berarti Anda bisa mencari percepatan sudut **tanpa perlu tahu besar gaya geseknya sama sekali**:

$$\tau_{gravitasi} = I_{kontak} \cdot \alpha$$

dengan teorema sumbu sejajar $I_{kontak} = I_{pm} + MR^2$. Untuk cakram pejal, $I_{kontak} = \tfrac{1}{2}MR^2 + MR^2 = \tfrac{3}{2}MR^2$. Persamaan langsung memberi α tanpa sistem persamaan yang rumit.

Satu rambu kejujuran yang perlu disampaikan ke siswa tingkat lanjut: titik kontak ini adalah **poros sesaat**, bukan poros tetap. Persamaan τ = dL/dt secara umum perlu kehati-hatian bila porosnya bergerak dan dipercepat. Untungnya, untuk kasus menggelinding ini, suku koreksi yang muncul kebetulan lenyap (karena kecepatan titik geometris kontak sejajar dengan kecepatan pusat massa), sehingga metode ini valid untuk dinamika sesaat. Yang tidak boleh dilakukan adalah memperlakukannya sebagai poros tetap untuk integrasi sepanjang waktu.

Ringkasnya: titik kontak diam sesaat, gesek statis tidak melakukan usaha (hanya memindahkan energi antar mode), dan menjadikannya poros adalah trik ampuh karena menghapus gesek dan normal dari persamaan torsi.
